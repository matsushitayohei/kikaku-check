# 企画チェック自動化設計書

**作成日**: 2026-08-03
**目的**: 施策リリース前の企画チェックにおいて、基本的な指摘事項をKIROで自動検出し、人の目を通すべき箇所を絞り込む

---

## 1. 現状の企画チェックフロー

```
企画者: Confluence仕様書作成（PJ概要 + 仕様詳細）
    ↓
企画者: Slack #team-pp1u-企画相談 に【企画チェック依頼】投稿
    ↓
レビュアー: Confluenceにインラインコメント ＆ Slackスレッドで議論
    ↓
企画者: 修正 → 「対応しました」
    ↓
レビュアー: 「解決済み」マーク or FIXリアクション
```

### レビュアー
- **浅利さん（G長）**: 事業方針・ABテスト設計・計測設計
- **五島さん（G長）**: 仕様の妥当性・方針確認・営業観点
- **齋藤さん**: 施策アプローチ・技術的実現性・tealiumイベント設計・分析設計

## 2. 指摘パターン分類（実データから抽出）

### カテゴリA: 自動化可能（チェックリスト的に機械判定可能）

| # | カテゴリ | 具体的な指摘例（実際のコメントより） | 検出ロジック |
|:---:|:---|:---|:---|
| A1 | **データ引用元URLの記載漏れ** | 「データの引用元のURL追加をお願いします」「Amplitudeのリンク先を見なくても大枠理解できるよう、どういうデータなのかは触れておいた方がよい」 | PJ概要内に数値（%、件数等）があるのにAmplitude/スプシURLがない箇所を検出 |
| A2 | **JIRAチケットのパス未記載** | 「JIRAチケットのパス記載をお願いします」 | PJ概要に `HDC-` や Jira URL がない場合に警告 |
| A3 | **Amplitudeのデバイス判定方法** | 「device_categoryは社内で利用していないのでOEM IDでの指定をお願いします（SP:10025, TB:10031, PC:48）」 | 仕様内に `device_category` の記載があれば「OEM IDを使用してください」と指摘 |
| A4 | **ABテスト: 1パターンに複数変更が入っている** | 「1つのチャレンジパターンに2つの変更を入れる形だと事後の効果検証の際にどの要素が良かったのか見えにくくなる懸念」「Phase1とPhase2に分けた方が施策結果を適切に学習して知見を得るためには良いのでは」 | テストパターン説明に変更点が2つ以上列挙されている場合に警告 |
| A5 | **Other metricsの不足** | 「一人当たりのお気に入り物件数も見たい」「問合せ種別の選択度合いの変化もお願いします」「各パラメータの設定率も見ていただくと良さそう」 | 施策内容に関連する標準的なOther metricsが設定されているか確認 |
| A6 | **Guardrail metricsの不足** | 「自動除外と課金額の確認もお願いします」 | Guardrail metricsに自動除外率・課金額が含まれているか（CRM/並び順変更施策の場合） |
| A7 | **tealium click_content: A/B両パターンでの取得** | 「比較対象のAパターンも送るのは厳しそうでしょうか。利用率が上がっているかの判断軸になる」 | click_content/show_contentのイベント設計がBパターンのみの場合に警告 |
| A8 | **tealium show_content: 表示イベントの取得漏れ** | 「物件一覧のスライダーが表示されたイベントを送っておくこと」「A側も飛ばした方がよい」 | UI変更施策でshow_contentイベントの定義がない場合に警告 |
| A9 | **選択肢が既存と同じかの明記** | 「選択肢は現行のプルダウンと同じである旨の記載があるとベター」 | UI変更施策で既存仕様との差分が明示されていない場合に注意喚起 |
| A10 | **PJ概要の書き方: 伝えたいことへのフォーカス** | 「伝えたいことにフォーカスする方が読み手の理解スピードが上がりそう」「もう少し根拠について深堀して書くとよさそう」 | 背景・課題の記述が冗長（既存仕様の説明が多く、変更点が不明確）な場合に注意 |
| A11 | **数値の根拠が不明確** | 「これはどのパターンの足し合わせでしょうか」「セグメントでclick_positionを指定すると時系列が逆になるケースも拾ってしまう」 | 数値の算出方法や集計条件が明記されていない場合に注意 |
| A12 | **step/ページの誤表記** | 「step2（次のも正確にはstep3）の誤表記でしょうか」「入れ替えるとありますが仕様書を見ると入れ替えではない」 | フォーム施策でstep番号の整合性チェック |

### カテゴリB: 半自動化可能（コンテキスト付きで注意喚起）

| # | カテゴリ | 具体的な指摘例 | 検出方法 |
|:---:|:---|:---|:---|
| B1 | **負荷・パフォーマンスリスク** | 「現状よりも変更しやすくなることで、該当件数を取得する処理回数が多くなることが予想されます。エンジニアと負荷の観点で問題ないか確認いただき」 | UI操作でAPIコールが増える施策（スライダー、リアルタイム更新等）の場合にリスク注意喚起 |
| B2 | **UIパターン別の表示崩れ確認** | 「物件一覧のFVはいろんな見せ方があるため、それぞれのパターンで表示崩れや意図しない見え方になっていないかの確認が必要」 | 物件一覧FV変更施策の場合に、既存パターン一覧を提示して確認を促す |
| B3 | **条件の曖昧さ: 表示トリガーの定義** | 「『3枚スワイプ』というのは『画像を3枚見た』ではなく『3回スワイプさせた（＝4画像目を見た）』でしょうか」「下のサムネイル画像をタップしたときも表示させてよいのでは？」 | 表示条件に曖昧な記述（「○枚スワイプ」「初回訪問時のみ」等）がある場合に詳細化を促す |
| B4 | **見学予約ボタンの表示条件** | 「『見学予約をする』は見学予約可物件（＝即入居可物件）のときにしか表示しないボタンなため、『その他の問合せ方法の下』といった表記の方がよさそう」 | 見学予約ボタンに言及する施策で表示条件の考慮漏れを指摘 |
| B5 | **非居住用物件への適用範囲** | 「非居住の場合でも同様にプルダウンがあり、対象外にするのも対象にするのも手間の度合いが変わらなければ、一気に変えてユーザー体験を統一化しておく選択肢もある」 | 検索条件変更施策で非居住用の考慮がない場合に確認を促す |
| B6 | **情報審査・営業チェックの要否** | 「広告費をもらって掲載しているので、CTAボタンすべて削除して問題ないか情報審査へ確認お願い」「段階料率の会員からすると料率の高い反響を誘導しているようにも思われる可能性も」 | CTA削除/変更・反響誘導に関わる施策で営業・情報審査チェックの有無を確認 |
| B7 | **計測指標の母数の妥当性** | 「母数が物件一覧を見た人、かつルートを限定するとこのCVRになってしまうため、母数をお気に入り登録したユーザー起点にしてはどうでしょうか」 | 効果測定メトリクスの母数定義が曖昧・不適切な場合に注意 |

## 3. 自動化チェックリスト（KIRO実装案）

### Phase 1: 仕様書の構造チェック（即時実装可能）

Confluenceページの構造を解析し、以下を自動チェック:

```
□ PJ概要にJIRAチケットURL（HDC-XXXX）が記載されているか
□ 数値データにAmplitude/スプシ等の引用元URLが付いているか
□ ABテストパターン説明で変更点が明確に列挙されているか
□ Guardrail metrics / Goal metrics / Other metrics がそれぞれ記載されているか
□ tealiumイベント設計（click_content/show_content）がある場合、A/B両パターンの設計になっているか
□ デバイス指定に device_category を使っていないか（OEM ID推奨）
□ 対象ページ/対象ユーザーの範囲が明確か（非居住用等の除外/包含が明記されているか）
□ step番号/画面名の整合性が取れているか
```

### Phase 2: 施策種別に応じた観点チェック（中期実装）

施策タイプを判定し、タイプ別の追加チェック:

| 施策タイプ | 追加チェック観点 |
|:---|:---|
| UI変更（フォーム系） | step番号整合性、入力項目の順序変更影響、反響の質への影響 |
| UI変更（一覧FV） | 既存パターン一覧との整合、表示崩れパターン網羅 |
| UI変更（CTA追加/変更） | フロートとの重複、営業/情報審査チェック要否 |
| 検索条件変更 | 負荷懸念（API呼び出し回数）、非居住用の考慮 |
| ABテスト | 1パターン1変更原則、A/B計測の対称性、母数定義の妥当性 |
| SEO施策 | index/noindex影響、canonical整合性、流入ロスリスク記載 |
| tealiumイベント追加 | 命名規則準拠、必須dataLayer、A/B両方での取得 |
| レコメンド/ロジック変更 | 自動除外率への影響、課金額への影響（Guardrail） |

### Phase 3: 過去指摘のナレッジベース活用（長期実装）

- 過去の企画チェックコメントをナレッジDBに蓄積
- 類似施策の過去指摘を参照して事前警告
- 「前回のPJ142で書かせてもらったコメントの観点がしっかり改善されている」のような文脈を活用

## 4. 自動化による期待効果

### Before（現状）
- レビュアー1人あたり: 1施策20〜40分（大型施策は1時間超）
- 指摘の50%以上が「記載漏れ」「形式的不備」「基本的な計測設計ミス」

### After（自動化後）
- KIROがカテゴリA（12項目）を自動チェック → 形式的不備をゼロに
- カテゴリBの注意喚起 → レビュアーが見るべきポイントを事前に整理
- レビュアーはカテゴリC（判断が必要な観点）に集中
- 予想削減時間: レビュアー1人あたり 10〜20分/施策（50%削減）

## 5. 実装アーキテクチャ案

```
[企画者] Confluenceに仕様書をFIX
    ↓
[トリガー] Slack #team-pp1u-企画相談 に【企画チェック依頼】投稿
    ↓
[KIRO Hook] メッセージ検知 → ConfluenceページIDを抽出
    ↓
[KIRO Skill] 仕様書を解析
    ├── 構造チェック（Phase 1）
    ├── 施策種別判定 → タイプ別チェック（Phase 2）
    └── 過去指摘参照（Phase 3）
    ↓
[出力] Slackスレッドに自動レビュー結果を投稿
    ├── ❌ 要修正（記載漏れ等）
    ├── ⚠️ 要確認（人の判断が必要な観点）
    └── ✅ 問題なし
    ↓
[レビュアー] ⚠️の観点に集中してレビュー
```
