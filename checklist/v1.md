# 企画チェックリスト v1

**作成日**: 2026-08-04
**ベース**: Confluenceコメント200件+ / Slackスレッド60件+の実データ分析
**対象**: 賃貸ものづくりチーム 施策リリース前の企画チェック

---

## 使い方

1. 仕様書をFIXする前に、該当するセクションのチェック項目を確認する
2. 施策タイプに応じて「施策タイプ別チェック」も確認する
3. チェックが全て通った状態で企画チェック依頼を出す

---

## A. ドキュメント基本要件（必須）

| # | チェック項目 | 確認観点 |
|:---:|:---|:---|
| A-1 | JIRAチケットURL（HDC-XXXX）がPJ概要に記載されているか | リンク切れも確認 |
| A-2 | 数値データにAmplitude/スプシ等の引用元URLが付いているか | 「データの引用元のURL追加をお願いします」の頻出指摘 |
| A-3 | 引用データの説明が、リンク先を見なくても大枠理解できる記載になっているか | 「どういうデータなのかは触れておいた方がよい」 |
| A-4 | PJ概要が「伝えたいこと」にフォーカスされているか（既存仕様の長文説明になっていないか） | 読み手の理解スピード向上 |
| A-5 | 対象ページ/対象ユーザーの範囲が明確か（非居住用等の除外/包含が明記されているか） | 曖昧な対象範囲は指摘頻出 |
| A-6 | 数値の算出方法・集計条件が明記されているか | 「これはどのパターンの足し合わせでしょうか」 |
| A-7 | 営業/情報審査/エンジニアなど確認相手・ステークホルダーが明示されているか | 「誰に確認中か」の明確化 |

## B. データ計測設計

| # | チェック項目 | 確認観点 |
|:---:|:---|:---|
| B-1 | デバイス判定に`device_category`を使っていないか | OEM IDを使用（SP:10025, TB:10031, PC:48） |
| B-2 | tealiumイベント（click_content/show_content）がA/B両パターンで取得する設計になっているか | 「比較対象のAパターンも送るのは厳しそうでしょうか」 |
| B-3 | UI変更施策で`show_content`（表示イベント）の定義があるか | 「表示されたイベントを送っておくこと」 |
| B-4 | show_contentの重複発火防止が考慮されているか | 「再度スクロールしても再発火させない」 |
| B-5 | Goal metrics / Other metrics / Guardrail metrics がそれぞれ記載されているか | 三種のメトリクスの網羅性 |
| B-6 | Other metricsに施策関連の追加指標が含まれているか | 「一人当たりのお気に入り物件数も見たい」等 |
| B-7 | Guardrail metricsに自動除外率・課金額が含まれているか（CRM/並び順変更施策の場合） | 副作用の早期検知 |
| B-8 | 効果測定メトリクスの母数定義が明確・適切か | 「母数をお気に入り登録したユーザー起点にしてはどうか」 |
| B-9 | Amplitudeチャートがファネル形式で正確な集計になっているか（add→removeの除外等） | 「ファネルにすべき」 |
| B-10 | tealiumイベントが他ページと混在しないか（イベント名の一意性） | 「物件一覧でも使われているイベントのため混ざる」 |

## C. ABテスト設計

| # | チェック項目 | 確認観点 |
|:---:|:---|:---|
| C-1 | 1パターンにつき変更点が1つになっているか | 「どの要素が良かったのか見えにくくなる」→Phase分割を検討 |
| C-2 | テスト計測期間と対象UU数の試算があるか | 「月間14万UU、2週間&50%で1パターン3.5万UU」の例 |
| C-3 | チャレンジパターンの配分比率がリスク許容範囲か | 75%チャレンジはリスク大 |
| C-4 | 勝った場合の次フェーズ（横展開先）が検討されているか | 「勝った場合に次にどこで試せそうか」 |
| C-5 | PC/SP同時テストの可能性が検討されているか | 「実装として重たくなければPCも一緒にテストしてみては」 |

## D. 仕様の網羅性

| # | チェック項目 | 確認観点 |
|:---:|:---|:---|
| D-1 | エッジケースが考慮されているか（0件/画像なし/非公開物件/複数枚等） | 「物件名が非公開の時は？」「画像がない会社の場合は？」 |
| D-2 | 既存機能との連動が考慮されているか（ヘッダーカウント/フロート/グリッド表示等） | 「グローバルヘッダーのカウントアップ/ダウンも連動すること」 |
| D-3 | 表示条件が具体的に定義されているか（「3枚スワイプ」= 3回 or 4画像目？） | 曖昧なトリガー条件は必ず指摘される |
| D-4 | 削除・解除時の挙動が定義されているか | 「この物件だけお気に入りしている状態でお気に入り削除したらフロートは何になる？」 |
| D-5 | UI状態パターンが網羅されているか（0件/1件/N件/閲覧中物件をお気に入り済み等） | 状態遷移の全パターン |
| D-6 | 選択肢が既存と同じかどうか明記されているか | 「選択肢は現行のプルダウンと同じである旨の記載があるとベター」 |
| D-7 | step番号・画面名が正確か（フォーム施策の場合） | 「step2（正確にはstep3）の誤表記」 |
| D-8 | 条件分岐が網羅されているか（間取り指定あり/なし、居住用/非居住用等） | 「ユーザーが1Rのみに絞った場合も同じ？」 |

## E. 事業観点・リスク

| # | チェック項目 | 確認観点 |
|:---:|:---|:---|
| E-1 | CTA削除/変更がある場合、情報審査への確認が行われているか | 「広告費をもらって掲載しているのでCTAすべて削除して問題ないか情報審査へ確認」 |
| E-2 | 反響誘導に見える変更がある場合、営業観点のチェックが行われているか | 「段階料率の会員からすると料率の高い反響を誘導しているように見える」 |
| E-3 | B2B画面への影響がある場合、告知・マニュアル記載が検討されているか | クライアント影響の考慮 |
| E-4 | データ引用の因果関係が正確か | 「動画を見る＝スクロール位置到達を指すため、CVRが高いとは限らない」 |
| E-5 | 出典表記が適切か（LIFULL HOME'S調べ等） | リスクヘッジと信頼性向上 |

## F. パフォーマンス・技術リスク

| # | チェック項目 | 確認観点 |
|:---:|:---|:---|
| F-1 | UI操作でAPIコールが増える施策の場合、負荷の観点で確認されているか | 「処理回数が多くなることが予想される。デバウンス等の対策を」 |
| F-2 | FV付近にCTAを追加する場合、フロートとの同時表示が考慮されているか | 重複表示の回避 |
| F-3 | 動画を含む施策の場合、再生制御（自動再生/音声OFF/停止条件）が定義されているか | 「動画サイトではないのでOFFにしていただきたい」 |
| F-4 | バッチ頻度に依存する記載がある場合、頻度変更時の影響が考慮されているか | 「バッチ頻度が変わったら記載も変更を」 |

## 施策タイプ別 追加チェック

### UI変更（フォーム系）

- [ ] step番号の整合性
- [ ] 入力項目の順序変更による反響の質への影響
- [ ] バリデーションルールの変更有無

### UI変更（一覧FV）

- [ ] 既存パターン（リスト/グリッド/マップ等）全てでの表示確認
- [ ] 表示崩れパターンの網羅

### UI変更（CTA追加/変更）

- [ ] フロートとの重複表示
- [ ] 営業/情報審査チェック要否
- [ ] 見学予約ボタンの表示条件（即入居可物件のみ）

### 検索条件変更

- [ ] API呼び出し回数増加による負荷
- [ ] 非居住用物件への適用/除外

### SEO施策

- [ ] index/noindex影響
- [ ] canonical整合性
- [ ] 流入ロスリスクの記載

### tealiumイベント追加

- [ ] 命名規則準拠
- [ ] 必須dataLayerの定義
- [ ] A/B両方での取得設計

### レコメンド/ロジック変更

- [ ] 自動除外率への影響（Guardrail）
- [ ] 課金額への影響（Guardrail）

## 自動化可能性の分類

### 現状（単体チェックリスト運用時）

| 分類 | 該当項目 | 割合 |
|:---|:---|:---:|
| 自動化可能（機械的に判定可） | A-1, A-2, B-1, B-2, B-3, B-5, B-7, D-7 | 35% |
| 半自動化（コンテキスト付き注意喚起） | A-4, A-5, B-6, B-8, C-1, C-2, D-1, D-3, E-1, F-1 | 40% |
| 人の判断必須 | 施策方向性, CTA文言, ABパターン最適設計, スケジュール調整 | 25% |

### lifull-mcps統合後（将来）

`lifull-growth/lifull-mcps` の各サーバーと連携することで、半自動化→自動化に昇格できる項目:

| 項目 | 連携先サーバー | 自動化方法 |
|:---|:---|:---|
| C-1: 1パターン複数変更 | confluence | 仕様書パターン記述をパースし変更点数をカウント |
| D-1: エッジケース未考慮 | db-explorer | テーブルのNULL許可カラム/状態カラムから想定ケースを自動列挙 |
| D-2: 既存機能との連動 | frontend-recipes | コンポーネント依存関係から連動対象を自動提示 |
| B-6: Other metrics不足 | bigquery | 施策タイプ×既存イベント定義から標準metricsの差分検出 |
| B-10: イベント重複 | bigquery | 既存tealiumイベント名との衝突を自動検索 |
| D-5: UI状態パターン | frontend-recipes + db-explorer | コンポーネント状態とデータ状態から全パターンを列挙 |

統合後の見込み: **自動化可能 50% / 半自動化 25% / 人の判断 25%**
