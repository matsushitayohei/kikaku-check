# 企画チェック自動レビュー スキル

## 概要
賃貸ものづくりチームの施策PJ概要/仕様書に対して、過去360件+のレビューコメントから抽出した指摘パターンに基づく自動チェックを実行する。

## トリガー
ユーザーが企画チェック対象のConfluenceページURL（またはページタイトル/PJ番号）を指定する。

## 実行フロー

### Step 1: 仕様書取得
- ConfluenceページIDからPJ概要と仕様ページの本文を取得
- `confluenceGetContent` で body.view を取得

### Step 2: 施策タイプ判定
本文のキーワードから施策タイプを判定:
- `フォーム` / `input` / `confirm` / `step` → **フォーム系**
- `一覧` / `list` / `FV` / `カード` → **一覧FV系**
- `CTA` / `ボタン` / `フロート` / `問合せ` → **CTA系**
- `検索条件` / `search` / `フィルター` → **検索条件変更**
- `SEO` / `canonical` / `noindex` / `h1` / `Lタグ` → **SEO**
- `tealium` / `click_content` / `show_content` → **tealiumイベント追加**
- `レコメンド` / `並び順` / `ロジック` → **レコメンド/ロジック変更**
- `ABテスト` / `パターン` / `チャレンジ` → **ABテスト**

### Step 3: チェック実行
以下のチェックカテゴリを順に実行:

#### A. ドキュメント基本要件（自動検出）
- [ ] JIRAチケットURL（`HDC-` or `jira.next-group.jp`）の有無
- [ ] 数値記載箇所にAmplitude/スプシURLの有無
- [ ] 対象ページ/対象ユーザーの範囲記載の有無（「対象」「スコープ」「除外」キーワード）
- [ ] 数値の算出方法・集計条件の記載有無

#### B. データ計測設計（パターンマッチ + 半自動）
- [ ] `device_category` の記載有無 → 「OEM IDを使用してください」
- [ ] click_content/show_content のA/B対称性（AパターンとBパターン両方の設計有無）
- [ ] Goal / Other / Guardrail metrics セクションの有無と充足度
- [ ] 母数定義の明記有無
- [ ] 施策タイプに応じた標準Other metricsとの差分チェック

#### C. ABテスト設計（構造解析）
- [ ] パターン記述の変更点数カウント（1パターン1変更の原則）
- [ ] テスト期間/対象UU試算の記載有無
- [ ] 配分比率の記載有無とリスク判定（70%超はリスク注意）
- [ ] 勝利時の次フェーズ検討有無

#### D. 仕様の網羅性（コンテキスト注意喚起）
- [ ] エッジケース言及の有無（「0件」「なし」「非公開」「画像なし」）
- [ ] 既存機能との連動（「ヘッダー」「フロート」「グリッド」言及有無）
- [ ] 表示条件の具体性（曖昧表現の検出:「初回」「N回目」「スワイプ」）
- [ ] 非居住用の考慮有無（検索条件/CTA変更施策の場合）

#### E. 事業観点（キーワード検出）
- [ ] CTA削除/変更 → 「情報審査チェック推奨」
- [ ] 反響/課金に影響する変更 → 「営業チェック推奨」
- [ ] B2B画面への影響 → 「マニュアル更新要否確認」

#### F. パフォーマンス（施策タイプ条件）
- [ ] リアルタイム更新/スライダー系 → 「負荷確認推奨」
- [ ] FV付近CTA追加 → 「フロートとの重複確認」

### Step 4: 結果整形

#### Goodセクションの判定基準
以下の観点で仕様書の優れた点を1〜3個ピックアップする:
- **データドリブン**: 数値の根拠が明確、Amplitudeチャート付き、サンプル数試算あり
- **過去施策の活用**: 関連する過去施策を複数参照し、教訓を明記している
- **仮説の解像度**: 「なぜ効くか」のロジックが明確で、ユーザー心理まで踏み込んでいる
- **テスト設計の質**: パターンの差分が明確、1パターン1変更の原則を守っている
- **リスク管理**: リスク＆対策が具体的、撤退基準が数字で定義されている
- **競合分析**: 競合のUI/機能を比較テーブルで整理している
- **ユーザーリサーチ**: インタビューやアンケートのファクトに基づいている
- **スコープの明確さ**: 対象/対象外が明確で、非居住用やデバイス差異も整理されている

企画者のモチベーションを上げつつ、チームの良い文化（データドリブン、仮説思考）を強化する意図で記載する。

出力フォーマット:
```
🤖 **企画チェック自動レビュー** （v1 / 360件+の実データパターンに基づく）

📋 **施策タイプ判定**: [判定結果]

---

👏 **Good**（この企画の優れた点）
- [仕様書の構成・仮説の質・データ活用・テスト設計などで特に良い点を1〜3個]

❌ **要修正**（記載漏れ）
- [自動検出で確実に欠けている項目]

⚠️ **要確認**（人の判断が必要な観点）
- [半自動検出: コンテキスト付き注意喚起]

💡 **提案**（過去の類似施策で頻出した追加観点）
- [施策タイプ別の追加チェック項目]

---
📊 チェック項目数: XX項目 / 検出: ❌X ⚠️X 💡X
📎 チェックリスト: https://matsushitayohei.github.io/kikaku-check/
```

### Step 5: Slackスレッドに投稿
- 指定されたスレッドに上記フォーマットで返信
- `slack_send_message` で `thread_ts` を指定してスレッド内に投稿

---

## 施策タイプ別 標準Other metrics テンプレート

### CRO（UI変更）系
- 物件詳細→フォーム遷移率
- input→confirm遷移率
- CTA利用率（新規追加パーツ）
- 直帰率
- 再訪率

### SEO系
- 対象ページの検索順位
- CTR（サーチコンソール）
- クロール量
- インデックス数

### ABテスト共通
- 反響の質（ありあり〜なしなし分解）
- 電話/見学予約の割合変化
- 自動除外率
- 課金額

---

## 制約
- Confluenceへの書き込みは行わない
- レビュー結果はSlackスレッド内にのみ投稿
- 「人の判断必須」カテゴリは注意喚起のみ（判断はしない）
- 過去施策のナレッジDB参照は未実装（Phase 3で対応予定）
